## Kernel Execution
The kernel primarily **executes on demand**, when a user-level program makes a system call, or a device sends an interrupt.

Some kernel threads operate asynchronously for housekeeping, which may include the kernel clock routine and memory management tasks, but these try to be lightweight and consume very little CPU resources.

Workloads that perform frequent I/O, such as web servers, execute mostly in kernel context. Workloads that are compute-intensive usually run in user mode, uninterrupted by the kernel.

It may be tempting to think that the kernel cannot affect the performance of these compute-intensive workloads, but there are many cases where it does. The most obvious is CPU contention, when other threads are competing for CPU resources and the kernel scheduler needs to decide which will run and which will wait. The kernel also chooses which CPU a thread will run on and can choose CPUs with warmer hardware caches or better memory locality for the process, to significantly improve performance.

### Interrupt threads


ISRs are designed to operate as quickly as possible, to reduce the effects of interrupting active threads (altrimenti il mio computer passa tempo a gestire interrupt piuttosto che a eseguire le mie applicazioni). If an interrupt needs to perform more than a little work, especially if it may block on locks, it can be processed by an interrupt thread that can be scheduled by the kernel.

- un interrupt thread è un thread appartenente al kernel, ma comunque un thread preemptible
    - al boot, il kernel crea anche questi 'kernel thread' che usa per servire l'utente
- l'interrupt thread è un classico worker thread che preleva workitems (puntatori a funzione) da una coda e li serve

On Linux, device drivers can be modeled as two halves, with the top half handling the interrupt quickly, and scheduling work to a bottom half to be processed later.

-  Handling the interrupt quickly is important as the top half runs in interrupt-disabled mode to postpone the delivery of new interrupts, which can cause latency problems for other threads if it runs for too long.
-  The bottom half can be either tasklets or work queues; the latter are threads that can be scheduled by the kernel and can sleep when necessary.

Linux network drivers, for example, have a top half to handle IRQs for inbound packets, which calls the bottom half to push the packet up the network stack. The bottom half is implemented as a softirq (software interrupt) that is raised by the top-half.


The time from an interrupt’s arrival to when it is serviced is the interrupt latency, which is dependent on the hardware and implementation. This is a subject of study for real-time or low-latency systems.

- c'è un ordine di grandezza di differenza nell'overhead di esecuzione di un ISR rispetto a questo bottom half
    - una causa sono ad esempio i cambi di contesto dell'interrupt thread
- questo dettagli sono importanti per sistemi real-time

### Interrupt Masking

Le ISR generalmente causano la disabilitazione degli interrupt

- ma non necessariamente, è supportato anche interrupt nesting
    - di nuovo, pensa ad real-time systems che deve gestire un evento super prioritario

Some code paths in the kernel cannot be interrupted safely. An example is kernel code that acquires a spin lock during a system call, for a spin lock that might also be needed by an interrupt. Taking an interrupt with such a lock held could cause a deadlock.

To prevent such a situation, the kernel can temporarily mask interrupts by setting the CPU’s interrupt mask register. The interrupt disabled time should be as short as possible, as it can perturb the timely execution of applications that are woken up by other interrupts.

```Parentesi OS Jitter 
Operating system jitter (OS jitter)—often called kernel jitter—refers to the unwanted delays, execution irregularities, and performance degradation experienced by an application because the CPU is occasionally stolen or interrupted by the operating system kernel to perform background maintenance tasks.

Even if your application is the only user program running on a dedicated CPU core, it is never truly alone. The OS kernel is constantly working behind the scenes, and that interference manifests as jitter.

Key Causes of OS Jitter
Beyond the periodic timer ticks you mentioned, several core kernel activities cause jitter:

Periodic Timer Ticks: The kernel relies on a regular timer interrupt (historically 100 Hz, 250 Hz, or 1000 Hz) to update system time, check process time slices, and handle timeouts. Every time this tick fires, the CPU is forced to interrupt whatever user-space code it was running to execute the timer handler.

Hardware Interrupts (IRQs) and Softirqs: As discussed with network drivers, when external hardware (NICs, disks, GPUs) needs attention, the CPU drops its current task to run the top-half IRQ and potentially trigger a softirq (ksoftirqd).

TLB Shootdowns: In multi-core systems, if one CPU core changes virtual memory mappings, it must force other cores to invalidate their Translation Lookaside Buffer (TLB) entries by sending an Inter-Processor Interrupt (IPI), pausing those cores momentarily.

Background Kernel Threads: Maintenance daemons, garbage collection, memory management (like kernel page reclamation or defragmentation), and CPU frequency/power scaling governors can wake up unpredictably and consume CPU cycles.

Why Does OS Jitter Matter?
For standard desktop applications or web servers, microsecond-level interruptions go completely unnoticed. However, OS jitter is a severe problem in domains requiring strict determinism and low latency:

High-Frequency Trading (HFT): If a kernel tick or softirq interrupts a trading algorithm for even 10 microseconds, a competitor might snatch a better price.

Real-Time Audio/Video Production: Jitter causes audible clicks, pops, or buffer underflows in digital audio workstations.

Industrial Automation & Robotics: Missing a tight control loop deadline because the CPU was handling a background task can cause physical instability or hardware failure.

High-Performance Computing (HPC) & Scientific Simulations: In massive MPI (Message Passing Interface) clusters running across thousands of nodes, performance is bottlenecked by the slowest node. If a single core gets hit by OS jitter, it lags behind, forcing all other synchronized nodes to wait at communication barriers.
```

# Come pensare al kernel

**NB**: Il kernel NON è un programma in esecuzione
- bisogna pensare al kernel come a una libreria/server
- l'unico momento in cui il kernel è "in esecuzione" è durante il boot. In tutto il resto del tempo, il kernel o sta servendo una syscall/interrupt/trap, oppure è idle su un core dato che non ci sono abbastanza task schedulabili per tutti i core
- dopo il boot se il kernel non sta servendo una system call/interrupt/trap, il kernel schedula l'idle thread
- questo thread fa poco e viene schedulato ogni tanto per gestire operazioni riguardanti power saving e quanto è in sleep un core
